# 페이지 유형별 일관성

[English](../page-families.md)

공통 컴포넌트와 단일 CSS 파일만으로 페이지 일관성이 보장되지는 않습니다.
UI 수정 전에 같은 유형의 기존 화면을 찾고 셸·본문 폭·제목과 본문 간격·카드 표면·타이포그래피·버튼 위치·반응형 규칙을 재사용합니다.
참고 이미지는 의도를 전달하지만 기존 앱의 공통 규칙을 대체하지 않습니다. 공통 클래스가 소유할 수 있는 값을 도메인 CSS에 복사하지 않습니다.

| 유형           | 비교 기준                                         | 공통 규칙과 허용되는 차이                                                                                                                                                                                    |
| -------------- | ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 설정           | `src/pages/settings/SettingsPage.tsx`의 일반 설정 | 공통 설정 셸·헤더, 기본 행은 `settings-general-content`와 `settings-row`를 사용합니다. 계정은 기존 프로필·사진·삭제 구성을 유지할 수 있습니다. 도메인 내용은 달라도 헤더 배치와 기본 표면은 동일해야 합니다. |
| 인증           | `src/pages/login/`의 로그인·가입·비밀번호 재설정  | 기존 인증 셸, 폼·검증·버튼 위치를 가장 가까운 폼 화면과 비교합니다.                                                                                                                                          |
| 목록·관리자    | `src/pages/admin/`, `notes/collections.md`        | 기존 검색·필터·표·목록·도구 모음·페이지 이동·상태 패턴을 재사용합니다. 열 차이가 새 도구 모음 디자인의 이유는 아닙니다.                                                                                      |
| 모달           | 공통 Modal과 기존 기능별 대화상자                 | 둥근 셸, 고정 헤더·푸터, 내부 스크롤, 포커스와 버튼 규칙을 공유합니다. 도메인 필드만 달라집니다.                                                                                                             |
| 독립 플랜 화면 | `src/pages/billing/PlansPage.tsx`                 | 설정 셸과 구분되는 전체 화면 닫기·스크롤 규칙을 유지합니다.                                                                                                                                                  |

새 유형은 두 번째 화면을 만들기 전에 기준 소유자와 공통 규칙을 이 문서에 등록합니다. 복합 화면은 영역별 유형을 구분합니다.
서로 다른 유형을 무조건 같은 크기로 만들지 않습니다. 예외는 범위와 이유를 기록하고, 공통 규칙 변경은 도메인별 덮어쓰기 대신 영향을 받는 화면에 함께 적용합니다.

## 필수 작업 기록

페이지·컴포넌트·앱 진입/라우팅·스타일 변경은 커밋 제목이 일치하는 작업 기록에 `# Page Family`와
`## Family`, `## Reference`, `## Shared Rules`, `## Exceptions`, `## Evidence`를 작성합니다.
구현 전에 비교 계획을 작성하고 커밋 전에 실제 결과와 테스트·산출물 경로로 갱신합니다.
단순 N/A·TODO·주석·다른 커밋의 기록으로는 통과하지 못합니다. 화면과 무관한 소스 변경은 영향이 없는 이유와 유효한 기존 검증을 명시합니다.
문서·테스트·훅만 바뀌는 경우 이 검토는 필수가 아니며 UI 삭제·이름 변경은 검사 대상입니다.

## 검증과 한계

`make verify-plan`과 `make verify`를 실행합니다. `make ui-composition-check`는 설정 헤더를 도메인 래퍼 안에 넣어 간격이 중복되는 구성을 거부합니다.
설정 헤더는 공통 셸의 직접 자식 또는 셸에 합성되는 프래그먼트 루트에 둡니다. 거버넌스는 같은 인덱스/커밋의 지침과 기록을 읽어 이전 커밋의 정책을 유지합니다.
거부·허용 Python 픽스처는 기본 `make check` 경로에서 실행됩니다.

시각적 변경은 모바일·데스크톱과 밝은·어두운 테마에서 비교하며 긴 번역문, 빈 상태·로딩·오류, 버튼도 해당 범위에 따라 확인합니다.
단순 넘침 검사 외에 브라우저의 실제 치수·계산된 스타일과 스크린샷을 확인합니다.
`tests/e2e/billing.spec.ts`는 390/1440px 양 테마에서 일반/결제 설정의 헤더 간격과 행 폭·패딩·테두리·곡률·배경을 비교하며 한국어 모바일과 등록 상태도 검증합니다.
새 레이아웃은 해당 유형의 비교 검증을 확장합니다.

정적 검사만으로 모든 페이지의 의미상 유형이나 시각적 동일성을 판단할 수는 없습니다. 작업 기록 검사는 기록의 존재를 강제하며 내용의 진실성을 보장하지 않습니다.
브라우저 비교도 등록된 사례만 다룹니다. 새 유형은 검토와 검증을 추가해야 하며 공통 컴포넌트 검사 통과만으로 배치 일관성을 주장하지 않습니다.

서버 연결 오류 화면은 쇼케이스 경로와 같은 메인 `AppLayout` 사이드바 및 공통 PanelCard 타이포그래피와 Button을 사용합니다. 기존 콘텐츠 영역 중앙에 최대 30rem 너비의 패널 하나를 배치하고 공개 네브바와 중첩 경고 카드를 제거합니다. 설정 재시도와 지연 로딩 표시는 기존 상태 소유자가 관리합니다.

키보드 설정은 일반 설정의 행·헤더를 재사용합니다. 두 앱 단축키를 계정별로 변경·복원하고 키 조합 카드를 눌러 편집하고 다른 곳을 누르면 취소합니다. 중복 조합만 거부합니다. 각 설정 섹션 전환은 기존 진입 애니메이션을 다시 실행합니다. 기본/캡슐 버튼은 드롭다운과 같은 32px 높이이며 터치 환경은 44px입니다. 프로필 구독 표시는 고정 16px 원과 중앙 정렬 글자를 사용합니다. 홈·관리자 제목은 설정처럼 아이콘을 생략합니다.

프로필 역할 배지는 사진 카드 안에 배치합니다. 옵션 드롭다운은 트리거 왼쪽 끝에서 오른쪽으로 펼치고 화면 경계에서 위치를 제한합니다. 삭제 옵션은 라이트·다크 모두 빨간색입니다. 키보드는 계정 아래에 배치하고 중복 키 안내는 토스트로 표시합니다.

결제 오류와 재시도는 해당 settings-row 카드 내부에 배치합니다. 로딩·오류 상태에서도 결제 카드의 최소 높이를 유지하고 관리자 목록 로딩은 테이블 영역 내부 Spinner로 표시합니다.

## Personal profile

`src/pages/profile/ProfilePage.tsx` is the canonical personal-profile family inside
the persistent AppShell. Use the existing 50rem content width and design tokens,
a centered identity hero, rounded editable avatar and three-part metadata strip.
At mobile widths the strip stacks into compact rows. This is intentionally distinct
from settings forms, matching the user-supplied profile reference without importing
its colors, fabricated statistics or showcase data. Edit/profile/password dialogs use
the existing Modal family. Account remains General-style settings rows.
